# Agent 记忆：轻松理解版

> **一句话：** Agent 记忆不是存聊天记录，而是一套“留下有用经验、需要时找回、发现不对就修正”的系统。真正有价值的记忆应跨会话，最好还能跨工具，并由开发者自己掌控。

## 1. 为什么需要 Agent 记忆？

真实工作会跨越多次会话：技术选型、已修复的 Bug、用户习惯、项目规则，都不能在下次对话中消失。因此，跨会话记忆已经成为 Claude Code、Codex、Cursor、Windsurf、GitHub Copilot 等工具的基础能力。

问题是，内置记忆通常彼此隔离：在一个工具里说清楚的偏好与项目约定，换到另一个工具仍要重新解释。理想状态是：**记忆跟着开发者和项目走，而不是跟着某个工具走。**

跨工具记忆主要有两条路：

1. **通用记忆服务**：如 Mem0、MemOS。多个工具通过 MCP 或集成访问同一个后端。
2. **人工维护说明文件**：如 `AGENTS.md`。透明、可审查，但不会自动积累和整理。

## 2. 记忆系统的五步循环

```text
抽取 → 组织 → 检索 → 更新 → 遗忘/压缩
```

更好记的版本是：**记下来 → 放整齐 → 找得到 → 改正确 → 清干净。**

### 抽取：什么值得记？

候选信息来自用户输入、模型输出、工具调用、环境状态和历史会话。关键是粒度与时机。

| 粒度 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 语义片段 | 保存原文并补足上下文 | 细节保真 | 易碎片化、库变大 |
| 实体事实 | 提炼为主体—关系—对象或属性 | 易关联与推理 | 需要结构化抽取 |
| 摘要 | 保留主要结论 | 节省空间 | 可能丢细节 |

常见时机有实时、异步、事件驱动、离线批量。实用设计是“快慢双链”：快链即时保留明确指令与约束；慢链后台去重、归纳并形成长期画像。

### 组织：存下来，不代表用得上

| 结构 | 特点 |
| --- | --- |
| 平铺 | 条目独立，以相似度检索为主；实现简单 |
| 树形 | 按主题或层级分类；先找范围，再找细节 |
| 图谱 | 用实体、因果、时序等关系连接记忆；支持多跳推理 |

图谱思路的代表是 HippoRAG：先抽实体关系，再把问题映射到图节点，通过个性化 PageRank（PPR）传播相关性，找回跨多条记录的证据。

### 检索：该查时查到对的版本

```text
判断是否需要记忆 → 构建查询 → 召回候选 → 重排筛选 → 注入上下文
```

触发检索有三类：输入驱动（用户直接问过去的事）、状态驱动（推理发现信息缺口或冲突）、策略驱动（为长期一致性主动查询）。被动检索是“现在需要才查”；主动检索是“提前查好，防止之后出错”。

### 更新与遗忘：记忆必须会变

新证据、用户反馈、偏好变化、环境变化和来源可信度变化，都可能让旧记忆需要更新。更新包括覆盖、合并、重组、巩固。新旧冲突时主要看：时效性、来源可信度、概率性共存（例如偏好可保留不同倾向和置信度）。

| 动作 | 含义 |
| --- | --- |
| 降权 | 降低被检索到的概率 |
| 归档 | 移出热索引，但保留备查 |
| 压缩 | 合并相似或重复内容 |
| 删除 | 清除无效内容，或满足隐私治理 |

遗忘很重要：过期、重复、冲突、低价值条目会污染检索、占用上下文，还可能让 Agent 基于错误前提推理。

## 3. 四类主流工程方案

### A. 前台模型自记

当前工作的模型自己判断“是否值得记”，再写入文件或记忆工具。

- **Claude Code**：以 `MEMORY.md` 为索引、主题文件保存细节；简单透明，但冲突判断主要依赖模型当下决定。
- **OpenClaw**：区分 `USER.md`、`MEMORY.md`、每日笔记、整理日志；后台 dreaming 从每日观察中归纳长期记忆，并做来源、预算和保留率校验。
- **Hermes-Agent**：按 Profile 隔离；`MEMORY.md`、`USER.md` 整体注入，历史会话进入 SQLite/FTS5；更新主要靠模型替换旧项。

优点是可检查、实现直接；局限是记录是否完整、冲突是否解决，很依赖模型的即时判断。

### B. 后台管线抽取

会话事件和工具调用被后台采集、压缩为观察记录，前台 Agent 不必停下来整理。

典型是 **claude-mem**：Hook 捕捉输入、工具调用、会话结束；Worker 将多段过程提炼成 Observation；本地用 SQLite FTS5，向量库 Chroma 可选；检索先给紧凑索引，再按时间线和 ID 深挖全文。

优点是可持续记录过程信息；局限是增加进程、模型调用和维护成本，长期结论也可能只是追加而缺少冲突治理。

### C. 抽取与归纳分离

先把每场会话提炼为候选，再与已有记忆去重、纠错、合并，最终形成长期知识。

- **Codex Memories**：先生成会话记录与回顾，再由归纳 Agent 更新常驻摘要。规则要求有来源支撑，后来的纠正覆盖旧说法，并区分观察、提议、完成、取代和不确定状态。
- **Gemini CLI Auto Memory**：生成针对 `MEMORY.md` 或 `GEMINI.md` 的补丁及 Skill 草稿，由用户在收件箱审阅、批准后写入。

优点是更适合管理跨会话变化和决策原因；局限是有处理延迟，也更复杂。

### D. 通用记忆中间件

这是独立记忆服务或带有状态运行时的 Agent 产品，适合多个工具共享。

| 系统 | 核心特点 |
| --- | --- |
| Mem0 | 向量与图结合，语义/BM25/实体等多路检索；平台 Dream 可做替代、合并、综合 |
| Zep / Graphiti | 将对话转化为具有时间关系的图谱，追踪实体关系变化 |
| Letta | 以有状态 Agent 运行时为中心管理记忆 |
| MemOS | 通过记忆单元、阅读器、调度器等组件管理生命周期 |

## 4. 评估方案时，重点看六件事

1. 能否跨会话、跨工具？
2. 能否隔离个人、项目、工作区、团队？
3. 能否处理重复、冲突、过期？
4. 是否会把无关内容大量注入上下文？
5. 是否能原样保留术语、数值和明确指令？
6. 用户能否查看、修正、删除自己的记忆？

结论：文件型方案强在透明可控；后台方案强在自动采集；两阶段方案强在长期整理；中间件强在跨工具复用。

## 5. CodeLory：它想解决什么？

CodeLory 不只是做聊天记录搜索，而是希望把编码中的约定、技术决策、排错经验、项目知识变成可复用、可治理的长期记忆。

- **跨工具复用**：Claude Code、Codex、CodeFactory 等可接入同一记忆服务。
- **作用域隔离**：个人偏好全局共享，项目知识按仓库隔离，避免不同项目串用。
- **长期治理**：写入时识别重复、补充、替代；可选 Auto Dream 做合并、分类和纠正。
- **受控检索**：结合语义、全文、图传播、实体链接，筛选和重排后再注入。

其后台采集方式参考 claude-mem：通过 Hook 接收会话事件，同时尽量不打断用户当前编码工作。

## 6. CodeLory 评测：最重要的结论

### 相比编码 Agent 的内置记忆

在 18 个场景中，CodeLory 的强项集中于：大历史检索、噪声干扰、跨会话组合、多跳推理、基础规范召回、部分超长会话和语义改写关联。

但不同产品各有优势：Claude Code 在显式记忆、精确术语、针式检索、时效判断和部分作用域隔离上更强；Codex 在稳定偏好归纳上更强；claude-mem 在某类超长会话的中段信息保留上更强；“没有证据时不要编造”这一能力，各家均达到 100%。

**复杂历史检索能力**和**逐字细节保真能力**是两种不同能力，不能用一个总分替代。

### 与 Mem0、MemOS 的对比

| 系统/配置 | 常规场景答准率 | 超长会话答准率 | 常规存储条数 | 超长会话存储条数 |
| --- | ---: | ---: | ---: | ---: |
| CodeLory 默认抽取 | 61.1% | 26.4% | 120 | 11 |
| CodeLory 放宽 1 档 | 75.7% | 58.3% | 408 | 51 |
| CodeLory 放宽 2 档 | 86.4% | 58.3% | 411 | 79 |
| Mem0 | 87.1% | 70.8% | 327 | 808 |
| MemOS | 87.4% | 83.3% | 417 | 1,557 |

放宽 2 档后，CodeLory 的常规场景已接近 Mem0、MemOS；主要差距仍在超长会话，尤其是会话中段的分散细节。Mem0、MemOS 为超长会话保存更多条目，体现事实覆盖率与存储/处理成本的取舍。

更细的结果：CodeLory 更新题连续三轮均为 21/21/21，冲突记忆约 90%，噪声干扰 100%，作用域隔离 93%。Mem0 的精确术语为 93%、语义漂移为 73%，在这两项更强；MemOS 的显式记忆为 97%、超长会话为 83.3%，在细节覆盖上更强。

CodeLory 放宽 2 档的存储条数不到 Mem0 一半、约为 MemOS 四分之一；入库耗时约为 Mem0 五分之二、MemOS 五分之一。注意：存储条数、入库时间、输入 token 是不同成本指标，不能机械合成“总成本”。

## 7. 线上数据：真实使用有没有帮助？

线上遥测快照为 **2026-09-13 00:00**，覆盖 v0.0.22 至 v0.0.24 约 10 天增量数据，判定模型为 Qwen3.8-27B。

- 按会话，主动检索得到的记忆平均 **53%** 被判为有效；平均每场会话获得 **2.3 条**有效记忆。
- 按用户，典型用户有效比例为 **43%**，中位数同为 43%。
- 按判定条数加权，有效占 **45.1%**、污染占 **17%**、误导仅 **0.5%**。
- 在产生影响的记忆中，约 **72%** 带来正向帮助；约 38% 为中性。

统计样本为 29 位实名用户、973 场会话、4,380 条判定。结论是：记忆已能带来明显帮助，但仍有不少记忆没有显著作用，检索相关性、投放时机和治理策略还需要持续优化。

## 8. 下一步：最值得优先做的事

1. **分段摄入超长会话**：不要只以整场会话为单位，减少中段细节丢失。
2. **保护关键原文**：术语、错误码、数值、配置名、明确约定要尽可能逐字保存。
3. **按信息量调整容量**：避免抽取过严导致事实遗漏。
4. **强化更新治理**：明确来源、时间、作用域和替代关系，避免过期内容复活。
5. **持续观测实际效用**：记录记忆是帮助、无关还是误导，把反馈用于优化检索与写入策略。
6. **沉淀可复用 Skill**：将重复验证的经验变为 Skill 候选，经用户审查后稳定复用。

## 9. 最后的口诀

> **记忆不是日志，而是可管理的经验。**  
> **先抽取，再组织；要会检索，更要会更新。**  
> **跨工具决定复用价值，作用域决定安全边界。**  
> **存得多不一定更好：关键是查得准、改得对、不过期。**  
> **最难的不是记住，而是在正确场景取回正确版本。**

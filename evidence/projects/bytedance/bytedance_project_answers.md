# ByteDance project evidence

## 1. 番茄 IP 热度模型看板

### 项目目的

- 服务于番茄头部 IP 影响力的持续监控与扩大。
- 监控 IP 热度指数的趋势变化，识别具有自传播迹象的高热度与高潜力 IP。
- 验证达人推书和市场宣发对 IP 影响力的提升效果，为后续宣发策略提供依据。
- 使用统一维度和数据口径，与其他出版方的头部 IP 横向比较，量化番茄 IP 的行业位置。
- 长期方向是与端内阅读及互动数据整合，形成全网热度指数并支持端内分发；该方向优先级较低，不应表述为已经完整落地。

### 负责内容与方法

- 建立网文 IP 热度评估指标体系，将消费、传播和搜索信号组织为三个核心维度。
- 整合内部数据和外部抓取平台数据，统一指标定义、统计粒度和更新时间口径。
- 建立自动化 ETL pipeline 汇总内部与外部平台数据；使用 PCA 生成客观统计权重，并通过跨部门共同确定的 AHP 权重纳入业务判断，拟合可横向比较、可按日跟踪的综合 IP 热度得分。
- 将综合评分流程部署至云端并搭建番茄 IP 热度业务看板，支持按 IP、出版方等维度进行横向比较，并按时间趋势进行纵向分析。

### 数据质量与自动化闭环

- 对外部抓取数据建立数据量、缺失、异常波动和更新状态监控，对指标异动进行上游追踪和口径归因。
- Bilibili：追踪视频日增 VV 的上游抓取与统计口径，修正长期不稳定、参考性较低的问题。
- Douyin：修正底层匹配逻辑并增加关键过滤条件，提高数据准确性和稳定性。
- Weibo：解决上游与下游数据粒度不一致的问题，统一可比口径。
- 传播和搜索模块：修正数据连接逻辑导致的缺失问题，提高指标完整性与数据利用率。
- Yunhe：协调业务更新逻辑与数仓更新逻辑，修复长期缺失、无法稳定参考的问题。
- 将多项人工更新流程迁移为线上自动化流程，并增加人工误填订正机制，减少人工维护和数据波动。
- 使用机器学习方法监测抓取平台的不稳定数据并进行预测填充，保障综合指数的连续性与参考价值。
- 自动化综合得分计算并加入上游数据异常监控，使异常发现、归因、口径订正和指数重算形成闭环。

### 业务使用与结果

- 看板按日监控 IP 热度变化，用于识别自然传播趋势、高热度 IP 和潜力 IP。
- 支持业务团队比较番茄与其他出版方头部 IP 的相对行业水平。
- 宣发活动后，业务团队使用看板观察趋势变化并评估达人推书和市场宣发效果。
- 随着数据口径持续订正和质量提升，看板成为 IP 宣发监控、推广建议和优先级判断的数据参考。
- 看板在内部目标用户中的 adoption 约为 60%。
- 本人最新补充：业务方参考 IP 热度调整投流后，业务复盘中团队负责的全部推广视频锚点链路 App 下载合计，相较调整前一个月约高 40%（前后各一个月）；不是单个关键 IP，也不是全 App 下载增长。调整前周度下载相对平稳，调整后多数周维持在更高且相对平稳的水平，而非单周异常尖峰。该周度趋势来自回忆，尚无原始周数据核验。

### 对外表述边界

- 用户已确认项目可命名为 `Fanqie IP Popularity Model & Dashboard`。
- 用户已确认可公开约 60% internal adoption；约 40% 为业务复盘中、参考 IP 热度调整投流前后各一个月，团队全部负责推广视频的锚点链路 App 下载合计的观察性差异，不是单个 IP 结果，也未证明策略造成了全部差异。总投流预算据本人回忆没有增加，尚待原始记录核实。
- 不应把端内分发写成已落地结果；只能作为长期产品方向。
- 不逐项披露各外部平台的数据故障，简历中概括为 automated data-quality monitoring and anomaly attribution 即可。

### 整体投流调整：已确认口径与待核验的归因框架（2026-10-13 更新）

**项目全链路（事实、业务方使用和机制解释分开）**

1. **场景与痛点（本人回忆）：**番茄 App 早期依靠推广视频的锚点链路获取下载；负责视频的周度锚点链路下载一度相对平稳。业务方约每 2–3 天参考单视频 VV、点赞和自身经验决定续投，但这些视频级表现不足以稳定比较不同 IP 的整体关注度和变化趋势；当时尚无固定的数据投流策略。这是预算约束下的续投优先级判断问题，不是本人独立负责的广告投放优化实验。
2. **本人建设的测量能力：**定义消费、传播、搜索三维 IP 热度指标，整合内部与外部数据，统一实体、粒度及更新口径；用自动化 ETL、数据质量及异常监控维护按日可比的信号。结合 PCA 得出的统计权重与业务共同商定的 AHP 权重，计算可跨 IP／出版方比较、可跟踪趋势的热度得分，并云端部署日更看板。该产品在内部目标用户中的采用率约 60%。
3. **业务方实际改变的决策（本人转述）：**业务方参考热度看板，调整哪些 IP 获得后续投流；投放选择、预算分配与执行是业务方负责。不能说本人制定了固定阈值、试投预算规则或自动分配算法。“VV 高但已有自然势头，继续投不一定有效；VV 低且主要靠付费曝光，继续投也可能无效；试投后观察 IP 趋势再决定续投”是解释为何多源趋势有用的**可能机制**，不是已从投放日志核验的固定操作规则或增量效果。
4. **投流后观察与复盘口径：**据本人回忆，前后各一个月的推广视频总量相近、总投流预算未增加，而团队负责视频的总曝光（付费和自然未拆分）增加。业务复盘近似数字为：调整后一个月，这些视频的锚点链路 App 下载合计较调整前一个月高约 40%；此前周度下载较平稳，调整后大多数周维持在较高且相对平稳的水平，不是单个 IP 或单周尖峰。周度走势、预算与曝光仍需原始报表核验；40% 不是每周涨幅，也不是全 App 下载涨幅。
5. **能说明与不能说明：**模型／看板提供了可比较的 IP 热度参考，并被业务方用于改变续投对象；之后同一团队负责视频的整体锚点下载出现观察性抬升。前后期对比不能单独证明由模型带来约 40% 因果增量；曝光未拆分，不能证明付费曝光效率、单次曝光下载转化率或单位预算获客效率提高。活动、周期、视频／IP 组合及自然扩散均不能视为已排除。投流稳定后再分析并固化策略属于可能的后续方向，不写成实习期已交付成果。

**已知事实与边界**

- 本人补充：产品早期尚无固定的数据投流策略，业务方过去约每 2–3 天主要参考 VV、点赞等决定续投及预算；看板上线后业务方表示参考 IP 热度，改变了哪些 IP 获得续投，而不是由本人决定投放或改变统一的试投预算与节奏。看板和热度模型是本人工作，投放决策与执行属于业务方。据本人回忆，前后负责推广的视频总量相近、总投流预算未增加，总曝光（未区分付费与自然）增加。业务复盘的近似结果为：调整前后各一个月，团队负责的全部推广视频锚点链路 App 下载合计约高 40%。调整前周度数据相对平稳，调整后多数周维持在更高且相对平稳的水平；没有原始周数据核验，也不能说每周均上涨 40%。本人曾提到「除去活动影响」，但尚未提供当时具体剔除逻辑、比较组和归因窗口。
- 看板用于**投流决策支持**，不能把约 40% 直接写成看板的独立因果贡献；锚点链路归因下载也不等于剔除自然量后的纯增量安装，更不等于全 App 下载增长。

**符合该项目逻辑、但尚需投放记录验证的策略假设（不是经历陈述）**

1. 已确认业务方参考 IP 热度改变哪些 IP 获得续投；可事后核对消费、传播、搜索组成的热度指数及续投前趋势，检查具体续投判断过程，不能把推测的量化阈值或固定策略当作当时已实施的政策。
2. 可核对调整前后的投放计划、素材/IP 组合及账单，确认预算、曝光、视频组合和营销活动如何变化；不能凭周度基准抬升反推出唯一策略差异。
3. 链路：看板提供 IP 热度参考 → 业务方调整哪些 IP 获得续投 → 按同一口径读取负责视频的锚点链路 App 下载 → 检查预算、曝光、活动和归因窗口是否可比。总曝光未区分付费和自然；若仅下载总量上升，不能据此说单位曝光效率提升，需另报 CPA/CPI 或每千次曝光下载数。

**如何处理「活动影响」（需按实际日志选择，不得倒填已做方法）**

- 首先定义结果：是否为去重的锚点链路**真实 App 下载/安装事件**，还是落地页点击/商店跳转；确定 campaign、IP、素材、渠道、日期、设备去重、点击/浏览归因窗口及跨渠道重复归因规则。仅有点击链路数据不能自动证明安装事件。
- 为新旧策略设置相同长度的投放观察窗及一致的转化归因窗，比较尽量相同的星期分布、渠道、目标、设备及促销强度；单纯「同期」不能控制预算、竞价、受众重叠、自然热度变化和素材质量。固定预算时可报同期归因 App 下载差；预算不同优先同时报告下载量和单位成本/曝光效率。
- 从活动日历标识平台级促销、IP 发布/联名/达人事件与其他大促。**可比的非活动时段**若同时存在，可预先划定观察窗，分别报告常规时段与活动时段的归因下载及趋势；如果活动只出现在新策略期，不能通过随意删掉「活动日」宣称已排除活动影响。保留原始全期结果并做敏感性分析。
- 若确有可比的未调整 IP、受众或地区与活动暴露记录，可考虑匹配对照或差分方法检查同期趋势及活动冲击；若要判断**新选品/投流政策相较旧策略的因果增量**，优先在相同可投放条件下做策略 A/B 或随机地区/受众 holdout，并统一预算与追踪窗口。没有随机试验或可信对照时，40% 只能叫「同口径锚点链路归因下载的观察性相对提升」（两轮是否属于严格同比尚待核实），不能叫「活动净化后的因果提升」。

**建议优先补证的原始记录**：锚点报表的指标字典与分母、前后各月具体日期与周度下载数据、纳入的全部推广视频清单、预算/曝光、选品前指数快照、投流调整记录、活动日历、转化归因和跨渠道去重配置、任何预先定义的活动剔除或对照报告。若无法找到依据，对外如使用约 40%，只作为业务复盘中同口径下载的观察性前后差异，不写「剔除活动后的增量」或「看板造成 40% 增长」。

**方法参照（供后续核对，不是这段实习已实际采用的技术）**：TikTok Ads Manager 的 App attribution 与 app install 事件定义说明归因口径需要核实；TikTok Conversion Lift 和 Google Research 的市场干预反事实研究说明「归因记录」与「因果增量」不是一回事。

## 2. 汽水音乐受众饱和度与拉新投放

### 项目目的

- 诊断推广视频锚点链路关联的新用户激活量下降；用户手机应用商店中的下载完成不可直接观测，不应将结果写作「激活到注册转化下降」或直接观测到的下载率下降。
- 排查可观测漏斗环节后，将观看用户中已安装汽水的比例持续上升识别为当前投放受众趋于饱和的证据；不能因此断言已排除全部其他原因。
- 区分已饱和垂类和仍有未安装用户触达及新激活潜力的垂类，将分析转化为差异化投放建议。

### 负责内容与方法

- 按抖音推广视频的去重观看用户分析汽水已安装状态，以已安装用户占比衡量创作者／内容垂类的受众饱和度；已安装用户不会产生新用户激活标识。
- 利用锚点链路关联的新用户激活，比较垂类在未安装用户中的激活表现，并结合未安装用户触达规模和变化趋势判断拉新潜力。应用商店下载不可见；视频与激活的关联涉及时间及其他相关特征，具体归因和去重规则仍待原记录核实，不应写为精确追踪每笔下载或已证明因果增量。
- 本人确认做过「已安装用户占比 × 新用户激活表现」四象限分析，并据此形成垂类投放建议；四象限是呈现和决策工具，不是机器学习模型。精确分母、阈值、是否按垂类展示规模与趋势需原记录核实，不倒填未确认的计算方法。

### 业务落地与结果

- 分层结论被市场团队实际采用。
- 市场团队减少对受众已趋于饱和垂类的常规投放，同时增加或试投了识别出的潜力垂类；本人未参与后续最终复盘。
- 可以描述业务采纳与投放方向调整；没有已确认的激活量 uplift、获客成本、ROI 或最终拉新效果，不虚构量化收益。

### 对外表述边界

- 最新本人确认的项目问题是**锚点链路关联新用户激活下降**，而非现有 CV／LinkedIn 旧稿中的 `activation-to-registration conversion` 下降；后续改写须同步纠正旧口径。注册与激活环节的具体顺序及内部事件定义以原记录为准。
- LinkedIn／简历应突出漏斗诊断、跨产品受众饱和测量、垂类拉新机会识别以及市场团队实际调整投放；四象限的绘制细节保留在本语料库和面试说明，不作公开经历中的主要技术亮点。
- 不能把四象限包装为预测模型、聚类或经实验验证的增量策略；不能把潜力垂类试投写成已确认的新用户激活改善。
- 可以说明 cross-product audience saturation 或 existing-user penetration；若涉及隐私或合规审查，则不展开底层用户 ID 匹配细节。定位为 incremental-user targeting and resource allocation，而不是泛化的 user segmentation。

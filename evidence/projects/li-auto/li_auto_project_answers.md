8. 我本人负责全流程所有部分
9. 推动了bms的custom strategy的设计，并进行ota升级，例如对ota的限制、温度的把控，提高寿命能力，同时基于这些drivers的结果反馈给电芯设计团队，进行新一代电池rd的边界测试。
10. 寿命风险 cohort 的预测方式：先根据机理变量和用户行为建立衰减模型，再基于车辆前期 SOH 序列拟合 SOH degradation slope；模型逐期将预测 slope 转换为下一期 SOH 值，并将新的 SOH 继续输入后续周期，递归推演至质保周期，从而识别可能跨过质保阈值的 cohort。对外表述只说明 warranty threshold，不披露具体阈值。
11. 已确认的可干预 driver 主要涉及充电 SOC 与温度，但 CV 对外不直接披露具体 driver，仅表述为 actionable user-behaviour drivers。实际策略由数据团队与性能部门共同设计：性能部门给出可实施的控制阈值及其对 driver 分布的模拟影响，数据侧将干预后的 driver 值逐期代入衰减模型，计算累计 SOH 轨迹变化。
12. 策略推演采用 simulation-based strategy mapping：对候选控制阈值、生效周期、目标 cohort 及策略组合进行参数扫描，形成 driver-to-strategy effect map，比较各方案对 SOH 轨迹、质保阈值失效规模和性能影响的预测结果。若未来在离散模拟点上另行拟合连续代理曲面，才可进一步称为 response-surface optimisation；当前不应声称使用了特定运筹求解器。
13. OTA 通常采用 staged, one-strategy-at-a-time rollout，以便和性能部门共同评估单项策略效果，再逐步拟合 cohort-level 策略及组合效果。上线后的六个月评估使用两类基准：（1）与 PSM 后相似、未实施策略的 control cohort 比较 SOH 分布及衰减轨迹；（2）同一车辆的实际 SOH 曲线与策略上线前拟合的 no-strategy counterfactual trajectory 比较。观察效果会回填质保期仿真，并据此预测单一车型可避免数千万元人民币质保成本；该数字为 projection，不是已确认的财务入账节省。
14. 方法边界：同一车辆上线后实际曲线与上线前拟合曲线的比较属于 model-based counterfactual trajectory comparison，不是标准 DiD。只有 treatment 与 PSM-matched control 均具有策略前后观测，并比较两组 SOH slope 的前后变化差时，才可称为 PSM-adjusted difference-in-differences。

## 2. Thermal-runaway / 热失控风险排序
1. 正样本指的是发生热失效的样本，正样本一般是10几：20w，10几：10几w，10几：70w，这样的极不平衡
2. 两个角度，一个是实现角度，二分类无论用何种模型目前都难以解决这种极不平衡的样本，而增加正样本量或者减少负样本量都难以合理进行，因此从二分类的原理出发，本来也是一个阈值然后基于probability进行分类，那么直接把probability当作风险也非常合理。另一个角度，业务背景本身对失效和未失效并非严格区分的01问题，未失效不等于不失效，他也有可能是失效样本，在未来的某个时候也会失效，同时我们要做监控，可解释性的去筛选高风险的车辆进行风险评估。本质是想要识别失效的高位电池表现和用户行为模式，筛选高分样本，进行风险监测。
3. 数据源这个我就不说了，你说的这些都有，还有用户的用车习惯，soc、温度、时间、电流等知类的
4. 这个就是都不一样，信号定义有差别，硬件结构也是，数据质量也是，异常信号等这些都很不一样，因此我每个平台进行数据质量处理后，在采用z_score进行平滑，因为用户是不会有太大区别，但需要从数据map回用户需要这样处理。我在这其中对ratio、sum、avg这些特征都是特殊处理，避免z_score引入一些特殊值，ratio和sum用的是median-quasi-z_score，减少z——score带来的异常0值处理。

  ## 2. 清洗与特征构造

  这一段分成“保留所有可评分车辆”和“筛选可训练车辆”两条线，避免因为训练资格不够而让车辆完全消失。

  ### 2.1 生命周期和训练资格

  每行会生成 training_eligibility。成为训练 normal 的基本条件是：

  1. 当前电池包的有效生命周期起点存在；

  4. 对 normal 训练样本，还要求所在 battery_platform 的合格样本数至少 1000。

  ### 3.2 特征选择

  训练不是 XGBoost 之类的黑盒分类器，而是 MannWhitneyModel 的规则型模型：

  1. 只选择数值列；排除 label 和 training_eligibility；
  2. 逐特征对 TR 与 normal 做双侧 Mann–Whitney U 检验；
  3. 去掉常值或极稀少变化特征，稀少变化的最低样本数是 30；
  4. 保留 p_value < 0.05 的显著特征；
  5. 计算原始效应量，并按 TR 覆盖率加权；
  6. M_gray 还要求原始效应量达到至少 0.5/覆盖率；
  7. 对显著特征计算相关性，使用层次聚类去掉高度相关的冗余特征；
  8. 每个相关性簇只留效应量最大的代表，最多 900 个；
  9. 对每个最终特征生成一条风险规则：方向（高风险是高值还是低值）、规则权重、TR 分布中位数和 MAD 尺度。

  所以它学习到的不是“一个不可解释的概率边界”，而是“哪些特征在 TR 与 normal 间显著不同，以及偏离 TR 风险方向时
  的风险强度”。见 batt-feature-platform-project/src/li_batt_feature_platform/tr_monthly/training.py:21、batt-
  feature-platform-project/src/li_batt_feature_platform/model_train/components/training/models.py:303。

  ## 4. 评分

  评分覆盖的是所有经过转换的正式样本，包括不满足训练资格的 normal 车；这也是训练集和评分集刻意分离的原因。

  对一条最终规则，模型先把车辆的该特征值与 TR 参考分布比较：

  1. 用 neg_loc 和 neg_scale 构造正态分布参考；
  2. 把输入裁剪到参考分布的 1%–99% 分位，避免极端值无限放大；
  3. 根据规则方向，取“偏高风险”或“偏低风险”的尾部概率；
  4. 将这个 0–1 的违规强度乘以特征权重；
  5. 对所有最终规则按权重归一化求和。

  形式上可以理解为：

  [
  risk(v)=\sum_f \frac{w_f}{\sum_j w_j}\times violation_f(v)
  ]

  每一项 feature_contribution_f 都保留，因此：

  [
  risk(v)=\sum_f feature_contribution_f(v)
  ]

  这不是经过 sigmoid 校准的“真实故障概率”；更准确的业务含义是相对 TR 风险模式的可比较风险分数。见 batt-
  feature-platform-project/src/li_batt_feature_platform/model_train/components/training/models.py:524。

  ### M_gray 的二次校准

  M_gray 会在训练集上，把最终规则映射到人工维护的风险维度标签，例如某一类热相关、充电行为相关或其他业务维度：

  1. 将同一维度下的特征贡献先汇总；
  2. 对每个维度重新计算 TR 与 normal 的 Mann–Whitney 效应量；
  3. 仅保留效应量至少为 0.5 的有效维度；
  4. 按维度效应量和该维度规则权重计算乘数；
  5. 用乘数重新缩放各特征贡献，再得到最终 Gray 分。

  因此 Gray 不是简单把特征“分组展示”，而是会根据维度级区分 TR/normal 的能力重新加权。见 batt-feature-
  platform-project/src/li_batt_feature_platform/tr_monthly/labels.py:47。

  ## 5. 排序

  排序策略与 profile 相关：

  - M_orig：对 normal 和 TR 全部样本按分数从高到低排，使用 pandas 默认的平均秩语义；
  - M_gray：normal 车辆只在 normal 池内排名，分数越高名次越靠前；
  - TR 不参与 normal 池排序，而是拿自己的分数插入 normal 分数分布，得到“如果它处在 normal 人群中会排第几”的参
    照名次。

  后者对业务更实用：TR 是标注案例、数量少且来源不同，把它们混在正常车池里会扭曲正常用户的运营排序。见 batt-
  feature-platform-project/src/li_batt_feature_platform/tr_monthly/ranking.py:8。

  ## 6. 解释

  解释分三层，且都保证可加和回总分。

  ### 6.1 特征级解释

  每个 VIN 输出：

  - scores
  - rank
  - 每个最终模型特征的贡献值 features

  ### 6.2 模型/特征元数据

  每个显著特征都会发布：

  - p-value、effect size、相关性 cluster；
  - 是否进入最终模型；
  - 风险方向；
  - 对于模型特征：weight、neg_loc、neg_scale；
  - 对 Gray 模型：所属风险维度及其标签来源；
  - normal 与 TR 的聚合分布证据、分位点和直方图信息。

  platform-project/src/li_batt_feature_platform/tr_monthly/publishing.py:863。

  ### 6.3 维度/雷达解释

  工作台读取已发布结果和 feature-info 后：

  1. 把特征贡献映射到 Gray 维度；
  2. 同一维度内求和；
  3. 生成风险雷达、维度瀑布图、特征下钻；
  4. 对比 normal 分布参考线及本次审计确认的 TR 案例。

### 2.4 可解释风险估分方法补充

每个最终入模特征均包含风险方向、规则权重和正常样本参考分布。评分支持三种分布映射方式：

- `norm`：基于正常样本的 location/scale 参数构造高斯参考分布，将特征值裁剪到 1%--99% 分位后通过 Gaussian CDF 映射为 0--1 风险贡献；低值风险特征使用反向尾部概率。
- `ecdf`：基于正常样本经验分布计算方向一致的经验分位风险贡献。
- `robust_ecdf`：在 ECDF 基础上使用有效样本长度进行稳健裁剪，降低极端分布和有限样本对估分的影响。

所有特征贡献均按规则权重加权，并除以总权重得到最终相对风险分数。最终分数可精确拆解为特征级贡献，因此模型输出同时支持排序、解释和业务维度汇总。该分数是相对于正常样本和历史失效证据的风险评分，不应表述为校准后的失效概率。

### 2.5 MLOps 与生产闭环补充

风险模型以按月离线训练和批量评分 pipeline 运行，生产交付包含 Docker 组件打包、内部 ML 平台调度、模型与规则版本管理、数据和模型质量门、结果发布及回读校验。已发布结果和规则通过 API 供风险工作台及单车临时估分消费，个案复核无需重新训练整套模型。

运行闭环包括月度批量执行、下游风险名单效果监测，以及新增确认失效案例自动进入下一轮训练、评分和风险名单产出。该机制实现基于新增 case 的持续模型更新，但不应写成高 QPS 实时 serving、Kubernetes 编排或独立 CI/CD ownership。

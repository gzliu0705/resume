# 岗位目录结构

每个 `applications/<岗位目录>/` 使用相同的分类规则；只创建有内容的目录，不用空文件夹或 `Final` 文件名虚构投递事实。

| 路径 | 放什么 | 状态边界 |
| --- | --- | --- |
| `README.md` | 目标职位、资料入口、本人确认与待核实信息 | 每个岗位必有 |
| `role/` | JD、公司研究、招聘方原始消息 | 外部背景，不用于证明候选人的项目数字 |
| `source/` | 可维护的简历源文件，如 TeX | 与 PDF 的对应关系若未验证，应标明 |
| `working/` | CV 内容稿、答案草稿、评估与以后尚未确认的 PDF 导出 | 无确认时不把 PDF 放进 `submitted/` |
| `submitted/` | 本人确认用于投递的文件 | 仅确认的 PDF 在此；文件时间不能代替投递日期 |
| `interview/` | 面试问题、准备笔记 | 有准备笔记不等于面试已经发生 |
| `work/` | LaTeX 日志、预览图、历史及重复导出 | 保留备查，不作为当前投递版本 |

Li Auto 与 ByteDance 项目证据在仓库顶层的 `evidence/projects/`，供所有岗位引用，不再放进某一岗位档案。[岗位索引](INDEX.md) 是全局入口；仓库根目录的 [FILE-MAP.tsv](../FILE-MAP.tsv) 记录此前从原目录到第一版结构的历史迁移，本次岗位目录重排见 [MOVE-MAP.tsv](MOVE-MAP.tsv)。两份映射是迁移记录，不是今后维护文件的目标目录清单。

2026-10-14，本人确认这十个岗位均已投递，使用各岗位目录下最新版本的 PDF。当前每个岗位在 `submitted/` 保存一份对应 PDF；用户未提供投递回执或具体发送日期，不能据此推断上传时采用的文件名和时间。

## 后续新增与更新

1. 新岗位在 `applications/<岗位目录>/` 建 `README.md`，记明岗位/招聘方、已知投递状态与确认依据、各现有材料的入口，以及待核实事项；在 [INDEX.md](INDEX.md) 增加一行。只按实际材料创建上述分类目录。
2. 新生成的 PDF 先放 `working/`；实际投递经本人确认后，将当时使用的原文件放入 `submitted/`，在该岗位 README 记录确认时间和投递文件路径。投递日期只有回执或本人确认时才填写。`source/` 中 TeX 与该 PDF 的生成关系未核对时不要声称一一对应。
3. 已投递的 PDF 保留原样。之后有新版稿件，不覆盖旧的 `submitted/`；如果同一岗位再次投递，则在 README 分别记录每次已确认版本，必要时以日期或明确的事件名区分文件，日期不可由本地修改时间推断。
4. 招聘方 JD 与消息归 `role/`；未证实发送的沟通稿归 `working/`；面试准备归 `interview/`，实际发生的面试或反馈必须单独标注。跨岗位复用的个人项目材料归仓库顶层 `evidence/`，不要复制多份到不同岗位。
